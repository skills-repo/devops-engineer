# 可观测性 Playbook

> 监控回答"**出问题了吗**"，可观测性回答"**为什么出问题**"。
> 前者靠预设的指标和告警，后者靠能在事后任意切片的高基数数据。两者都要有。

## 一、三支柱及其取舍

| 支柱 | 回答什么 | 成本 | 基数容忍度 |
|------|---------|------|-----------|
| **Metrics** | 有多少、多快、多少错 | 低（预聚合） | 低——每个 label 值组合都是一条时间序列 |
| **Logs** | 具体发生了什么 | 高（全量存储） | 高 |
| **Traces** | 一个请求在系统里经过了什么 | 中（可采样） | 高 |

选择顺序：**先建 metrics 和告警**（成本低、覆盖广），
再建 traces（定位跨服务问题），日志按需分级留存。

反过来做的团队常见结局：日志账单失控，但仍然不知道服务健不健康。

## 二、Metrics：四个黄金信号

不要一上来设计几十个指标。每个服务先确保这四个：

| 信号 | 指标 | 告警方向 |
|------|------|---------|
| **Latency** | 请求耗时分布（P50/P95/P99） | P99 超阈值 |
| **Traffic** | QPS / RPS | 断崖式下跌（比上涨更危险） |
| **Errors** | 错误率 | 错误率超阈值 |
| **Saturation** | CPU/内存/连接池/队列深度 | 接近上限 |

对资源型系统（数据库、队列）用 **USE**：Utilization、Saturation、Errors。

### 指标设计的三个坑

**坑 1：用平均值**

```
✗ avg(response_time)        平均 200ms 可能是 99% 的 50ms + 1% 的 15s
✓ histogram_quantile(0.99, ...)
```

平均值会掩盖长尾，而长尾正是用户投诉的来源。**永远看分位数**。

**坑 2：高基数 label**

```
✗ http_requests_total{user_id="...", request_id="...", url="/user/12345"}
✓ http_requests_total{route="/user/:id", method="GET", status="200"}
```

把 user_id 放进 metric label，一百万用户就是一百万条时间序列，直接打爆存储。
**高基数信息属于 logs 和 traces，不属于 metrics**。

**坑 3：只监控技术指标**

CPU 正常、错误率 0，但订单量掉了 90%——技术指标全绿的故障最难发现。
关键业务指标（订单数、支付成功率、注册数）也要进监控。

## 三、Logs：结构化 + 分级

### 结构化日志

```json
{"ts":"2026-08-06T00:12:03Z","level":"error","service":"api","trace_id":"a1b2c3",
 "user_id":"u_889","route":"/orders","err":"db timeout","duration_ms":5031}
```

纯文本日志无法聚合分析。用 JSON，且**每条日志带 trace_id**——这是打通三支柱的关键。

### 日志级别的实际含义

| 级别 | 用于 | 生产是否开 |
|------|------|-----------|
| ERROR | 需要人介入的问题 | 是，且应有告警 |
| WARN | 异常但已自动处理（重试成功、降级） | 是 |
| INFO | 关键业务事件（下单、支付、登录） | 是，控制量 |
| DEBUG | 排查用的详细信息 | 否，按需临时开启 |

**反模式**：把 INFO 当 DEBUG 用，每个函数入口都打日志。
结果是日志量爆炸、成本失控、真正的错误被淹没。

### 成本控制

```
热存储（可搜索）  7–14 天    ERROR + WARN + 采样的 INFO
温存储           30–90 天    压缩归档，需要时再加载
冷存储/对象存储   1 年+       合规留存，几乎不查
```

高频重复日志做采样（如每 100 条记 1 条 + 计数）。

## 四、Traces：跨服务定位

一个请求的完整链路，能直接看出：哪个服务慢、哪次数据库查询是瓶颈、
哪个下游超时导致了上游雪崩。

### 落地要点

- **用 OpenTelemetry**，不要绑定单一厂商的 SDK。后端可换，埋点不用重写
- **trace context 必须透传**：HTTP header、消息队列的 message attributes、
  异步任务的上下文。断在哪里，链路就断在哪里
- **采样策略**：
  - 头部采样（简单）：固定比例，如 1%
  - **尾部采样（推荐）**：先全采，请求结束后决定——保留所有错误请求和慢请求，
    正常请求按比例留。这样既控成本又不丢关键样本
- **span 上挂高基数属性**（user_id、order_id），这是 traces 相对 metrics 的核心优势

## 五、告警设计：宁缺毋滥

### 唯一标准

> **一条告警响了，是否需要人立刻做点什么？**
> 答案是"不"的告警，应该删掉或降级为看板指标。

告警疲劳是可观测性建设的头号失败模式。一旦团队开始习惯性忽略告警，
真正的故障也会被忽略。

### 分级

| 级别 | 触发 | 通知方式 |
|------|------|---------|
| **P1 / Page** | 用户可感知的服务不可用 | 电话/短信，7×24 |
| **P2 / Ticket** | 需要处理但不紧急（磁盘 70%、证书 30 天到期） | 工单/IM，工作时间 |
| **P3 / Info** | 仅记录，看板可见 | 不主动通知 |

### 基于症状而非原因

```
✗ "CPU > 80%"                    CPU 高不等于用户有感知
✓ "P99 延迟 > 1s 持续 5 分钟"     用户真的在等
✓ "错误率 > 1% 持续 3 分钟"
```

原因型告警（CPU、内存）留作排查线索和 P2，不要 page 人。

### 减少误报的技巧

- **持续时间**：`for: 5m`，避免瞬时抖动
- **多条件组合**：错误率高 **且** 请求量不低（低流量时 1/2 就是 50% 错误率）
- **抑制关系**：集群整体故障时，抑制其下所有服务的子告警
- **可操作性**：每条告警必须带 runbook 链接，说明「先看什么、怎么处理」

## 六、SLO 与错误预算

```
SLI  = 好请求数 / 总请求数
SLO  = SLI 的目标，如 99.9%
错误预算 = 1 - SLO = 0.1% ≈ 每月 43 分钟不可用额度
```

### 错误预算怎么用

| 预算状态 | 行动 |
|---------|------|
| 充足 | 可以加快发布、做有风险的变更 |
| 消耗过半 | 提高变更审慎度 |
| 耗尽 | **冻结功能发布，全力投入稳定性** |

这把"要稳定还是要速度"的主观争论变成了数据决策。

### 燃烧率告警

比"错误率 > X%"更合理的告警方式：

```
快燃烧：1 小时内消耗了 2% 的月度预算   → P1 立即处理
慢燃烧：6 小时内消耗了 5% 的月度预算   → P2 当天处理
```

这样既能抓住突发大故障，也能抓住"每分钟错一点、一周耗光预算"的慢性问题。

### SLO 设定原则

- 从**用户视角**定义，不是从组件视角（"下单接口成功率"而不是"数据库可用率"）
- 100% 不是目标。追求 100% 的成本是无限的，且会扼杀所有变更
- 内部依赖的 SLO 必须严于对外承诺的 SLO
- 先测量一个月现状，再定 SLO。凭空定的 SLO 要么永远达标（无意义）要么永远不达标（被无视）

## 七、落地顺序

给一个从零开始的团队：

```
1. 每个服务暴露四个黄金信号 + 健康检查端点
2. 建一个"服务概览"看板：QPS / 错误率 / P99 / 饱和度
3. 建 3–5 条 P1 告警（不要更多），每条带 runbook
4. 结构化日志 + trace_id 贯穿
5. 接入 OpenTelemetry traces，尾部采样
6. 定义核心链路的 SLO，配燃烧率告警
7. 每次故障后回看：当时的数据够不够定位？不够就补
```

**第 7 步是最重要的**。可观测性不是一次建成的，是每次故障后补出来的。
每个 incident 复盘都应该产出一条"下次要能更快看到 X"的改进项。
