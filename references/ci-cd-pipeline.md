# CI/CD 流水线 Playbook

> 流水线的目的不是"跑测试"，是**用最短的反馈时间挡住最多的问题**。
> 一条 40 分钟才告诉你 lint 失败的流水线，比没有流水线更糟——它训练团队忽略 CI。

## 一、分层门禁：按成本排序

把检查按「执行成本 / 反馈价值」排序，快的先跑，贵的后跑：

```
阶段 0  (<10s)   格式化检查、commit message、文件大小
阶段 1  (<1min)  lint、类型检查、依赖漏洞扫描
阶段 2  (<5min)  单元测试、构建
阶段 3  (<15min) 集成测试、容器镜像构建 + 扫描
阶段 4  (<30min) E2E、性能基线、契约测试
```

**fail-fast**：前一阶段失败立刻终止，不浪费后续资源。
**阶段 0–2 必须在 5 分钟内给出结论**——这是开发者愿意等待的上限。

### 什么该阻断，什么只该警告

| 检查 | 阻断 | 理由 |
|------|------|------|
| lint / 类型错误 | ✅ | 零容忍，修复成本极低 |
| 单元测试失败 | ✅ | 功能回归 |
| 覆盖率**下降** | ✅ | 比"覆盖率低于 X%"更合理 |
| 覆盖率低于绝对阈值 | ⚠️ | 老项目会永久卡住 |
| 高危 CVE | ✅ | 有修复版本时 |
| 中低危 CVE | ⚠️ | 阻断会导致团队批量加白名单 |
| 镜像体积增长 | ⚠️ | 提示即可 |
| E2E 偶发失败 | ⚠️ → 修 | 不稳定测试比没测试更有害，应隔离而非重试掩盖 |

**原则**：阻断项必须是"确定性的、可立即修复的"。不确定的检查一旦阻断，
团队学会的第一件事就是绕过它。

## 二、提速：四个杠杆

流水线慢的根因通常就这四个，按收益排序排查：

### 1. 缓存（收益最大）

```yaml
# 依赖缓存：key 必须包含 lock 文件哈希
key: deps-${{ runner.os }}-${{ hashFiles('**/pnpm-lock.yaml') }}
restore-keys: deps-${{ runner.os }}-

# 构建缓存
- Docker: BuildKit 内联缓存 / registry 缓存
- Turborepo / Nx: 远程缓存，跨 CI 和本地共享
- 编译型语言: 增量编译产物目录
```

**缓存失效的常见错误**：key 里放了 `github.sha`（每次都变，等于没缓存）、
只设 `key` 不设 `restore-keys`（lock 一变全部冷启动）。

### 2. 并行

- 独立的 job 并行跑（lint / test / build 三条线互不依赖）
- 测试分片：按文件或历史耗时切成 N 份并行
- monorepo：只跑受影响的包（`turbo run test --filter=...[origin/main]`）

### 3. 只跑必要的

```yaml
on:
  pull_request:
    paths:
      - 'apps/api/**'
      - 'packages/shared/**'
```

单体仓库不做路径过滤，会导致改一行文档跑全量 E2E。

### 4. 换机器

CPU 密集型任务（构建、编译）升级 runner 规格的性价比通常高于优化代码。
先测一下 2 核 vs 8 核的实际差异再决定。

## 三、密钥与权限

### 绝不能做

- 密钥写进代码或 CI 配置文件
- `pull_request_target` 事件里 checkout 并执行 PR 代码（可被 fork 窃取密钥）
- 给 CI token 全仓库写权限（默认应是只读）
- 在日志里 echo 环境变量

### 应该做

```yaml
permissions:              # 显式最小权限，覆盖默认值
  contents: read
  id-token: write         # OIDC 换取云凭证，不存长期密钥
```

- **OIDC 联邦身份**优于长期 access key：GitHub Actions / GitLab CI 都支持向
  AWS/GCP/Azure 换取短期凭证，无需存储密钥
- fork PR 默认不注入密钥；需要密钥的 job 拆到合并后或用 environment 保护规则
- 密钥轮换周期入日历，不要"设一次用三年"

## 四、分支与触发策略

| 策略 | 适用 | 代价 |
|------|------|------|
| **主干开发 + feature flag** | 高频发布、团队协作紧密 | 需要 flag 治理，否则 flag 债累积 |
| GitHub Flow（短分支） | 大多数团队的默认选择 | 分支活过 3 天就开始有合并痛苦 |
| Git Flow（develop + release） | 有明确版本发布节奏的产品 | 重，多数 web 项目不需要 |

**共识**：长期分支是万恶之源。分支存活时间应以**小时/天**计，不是周。
需要"半成品先合入"时用 feature flag，不要用长期分支。

### 触发矩阵

```
PR 打开/更新   → 阶段 0-3（快速反馈）
合入主干       → 全量 + 构建产物 + 部署到预发
打 tag         → 生产部署（需人工审批）
定时（每日）   → 全量 E2E + 依赖漏洞扫描 + 性能基线
```

## 五、构建产物与可追溯

一次构建，多处部署（build once, deploy everywhere）：

```
构建阶段产出不可变产物（镜像/包）→ 打上 commit SHA
   ↓
预发部署该产物 → 验证
   ↓
生产部署同一个产物（不重新构建）
```

**为每个环境重新构建是常见反模式**——预发验过的和生产跑的不是同一个二进制，
验证等于白做。

产物必须能回答：这是哪个 commit 构建的、什么时候、用什么依赖版本。
镜像打 label，或生成 SBOM（见 `secrets-and-security.md`）。

## 六、流水线本身的可维护性

- **配置即代码**，和应用代码同仓、同 review
- 复用：GitHub Actions 用 composite action / reusable workflow；GitLab 用 `extends` + `include`
- 本地可复现：关键检查提供 `make ci` 之类的本地入口，不要只能在 CI 上跑
- 不要在 YAML 里写超过 10 行的 shell——移到脚本文件，可测试可复用

## 七、诊断清单

| 症状 | 排查 |
|------|------|
| 流水线越来越慢 | 看各阶段耗时趋势；90% 情况是缓存失效或没做路径过滤 |
| 偶发失败，重跑就好 | 不稳定测试或共享资源竞争。**不要加自动重试掩盖**，隔离并修复 |
| 团队习惯性绕过 CI | 反馈太慢或误报太多。先砍掉低价值阻断项，再提速 |
| CI 通过但生产出问题 | 环境差异。检查是否 build once、配置是否外置 |
| 密钥泄漏 | 立即轮换 → 查 CI 日志 → 检查 fork PR 配置 |
