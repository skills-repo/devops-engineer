# 故障响应 Playbook

> 故障响应的第一目标是**恢复服务**，不是找出根因。根因分析放在事后。
> 一线最常见的错误就是在服务还挂着的时候埋头调试。

## 一、分级

| 级别 | 判定 | 响应 | 通知 |
|------|------|------|------|
| **P0** | 核心业务完全不可用 / 数据损坏风险 | 立即，全员可召 | 全员 + 管理层 |
| **P1** | 核心功能严重降级，多数用户受影响 | 15 分钟内 | 值班 + 相关负责人 |
| **P2** | 部分功能受影响，有绕行方案 | 1 小时内 | 值班 |
| **P3** | 轻微影响，用户基本无感 | 工作时间处理 | 工单 |

**判定看用户影响，不看技术严重性**。一台机器挂了但流量已自动切走 = P3；
一个配置项写错导致所有用户看到错误页 = P0。

## 二、角色分工（P0/P1）

超过 2 人参与的故障必须分角色，否则会出现"三个人同时改生产"：

| 角色 | 职责 | 不做什么 |
|------|------|---------|
| **Incident Commander** | 决策、分工、控制节奏 | **不亲自动手排查** |
| Ops Lead | 执行操作（回滚、扩容、切流） | 不对外沟通 |
| Communicator | 对内对外同步进展 | 不参与技术决策 |
| Scribe | 记录时间线 | — |

小团队一人可兼多角，但 **IC 和动手的人必须分开**。
IC 一旦陷入调试，就没人看全局了。

## 三、响应流程

```
1. 确认    这是真故障还是误报？影响范围多大？
2. 定级    P0/P1/P2/P3，拉起对应响应
3. 止血    优先恢复，不追根因
4. 恢复    确认指标回到正常水位
5. 复盘    24–72 小时内完成
```

### 止血手段（按优先级尝试）

```
1. 回滚最近的变更          ← 70% 的故障源于变更，这是第一选择
2. 关闭相关 feature flag
3. 扩容 / 重启
4. 降级：关闭非核心功能，保住主链路
5. 限流：牺牲部分请求保住系统不雪崩
6. 切流：切到备用区域/集群
```

**最近有变更就先回滚**。不要在"是不是这次变更导致的"上争论超过 2 分钟——
回滚的成本远低于继续排查的时间成本。

## 四、排查路径

### 第一个问题：最近改了什么

```
□ 代码部署？      查部署记录，时间点是否吻合
□ 配置变更？      配置中心、feature flag 的变更日志
□ 基础设施变更？  terraform apply 记录、云控制台操作日志
□ 依赖方变更？    上下游服务是否同期发布
□ 数据变更？      是否有批量任务、数据修复脚本
□ 外部因素？      流量突增、DDoS、云厂商故障、证书过期
```

**证书过期和磁盘满是两个经典的"什么都没改却挂了"**，值得单独检查。

### 分层定位

从用户侧往下逐层排除，每层都问"这一层是好的吗"：

```
用户 → DNS/CDN → 负载均衡 → 网关 → 应用 → 缓存 → 数据库 → 依赖服务
```

用可观测性数据快速定位：

- **错误率在哪一层开始升高** → 问题就在那一层或它的下游
- **延迟在哪一段变长** → 看 trace 的火焰图
- **是全量还是部分** → 部分则看是哪个实例/区域/用户群

### 常见故障模式

| 现象 | 常见原因 |
|------|---------|
| 突然全挂 | 配置错误、证书过期、依赖服务全挂、部署事故 |
| 缓慢劣化 | 内存泄漏、连接池耗尽、磁盘写满、日志堆积 |
| 周期性抖动 | 定时任务、GC、缓存集中过期、上游批量调用 |
| 部分实例异常 | 单机问题、滚动更新中、节点资源不足 |
| 错误率随流量上升 | 容量不足、下游限流、连接池太小 |
| 上下游雪崩 | 缺熔断和超时，一个慢服务拖垮全链路 |

## 五、沟通模板

对内每 15–30 分钟同步一次，即使没有进展：

```
【状态】调查中 / 已定位 / 修复中 / 已恢复
【影响】哪些功能、影响多少用户、从什么时候开始
【当前动作】正在做什么
【下次更新】XX:XX
```

对外（用户/客户）：

- 承认问题、说明影响范围、给出预期，**不要给不确定的恢复时间**
- 不在故障期间归因（"是云厂商的问题"这类话事后经常打脸）
- 恢复后发一份简要说明

## 六、复盘：对事不对人

### 无指责原则（Blameless）

前提假设：**每个人在当时的信息和约束下都做了他认为正确的决定**。
如果结论是"某某不该点那个按钮"，那说明真正的问题是**系统允许一次误点就造成故障**。

指责会导致隐瞒，隐瞒会导致同样的故障再次发生。

### 复盘文档结构

```
1. 摘要        一段话：发生了什么、影响多久、多少用户
2. 时间线      精确到分钟，从第一个异常信号到完全恢复
3. 影响        量化：受影响请求数、订单数、时长、SLO 预算消耗
4. 根因        用 5 Whys 追到系统性原因，不止步于"某代码有 bug"
5. 做对了什么  值得保留的响应动作
6. 改进项      每条都有 owner + 截止日期 + 优先级
```

### 时间线的四个关键时刻

```
T0  问题实际开始
T1  监控发现（T1 - T0 = 检测时间，应该趋近于 0）
T2  人开始响应（T2 - T1 = 响应时间）
T3  服务恢复（T3 - T2 = 修复时间）
```

**如果 T1 - T0 很大，说明监控有盲区**——这通常比故障本身更值得改进。
很多团队复盘只关注 T3-T2，忽略了"为什么我们是被用户告知的"。

### 5 Whys 示例

```
服务挂了 → 为什么？
数据库连接池耗尽 → 为什么？
一个慢查询占满了所有连接 → 为什么？
新上线的接口缺少索引 → 为什么？
上线前没有慢查询检查 → 为什么？
CI 里没有这项检查        ← 真正的改进点
```

止步于第二层（"加个索引"）只能防住这一次，
追到第五层（"CI 加慢查询检查"）才能防住这一类。

### 改进项质量标准

```
✗ "加强代码 review"           不可执行、无法验证
✗ "以后注意"                  没有 owner 没有期限
✓ "CI 增加 EXPLAIN 检查，扫描新增 SQL 是否走索引 — @张三 — 8/20"
✓ "数据库连接池加饱和度告警，阈值 80% — @李四 — 8/15"
```

**没有完成期限和 owner 的改进项等于没写**。复盘的价值全部在改进项的落地率上。

## 七、平时的准备

故障响应的质量取决于平时的准备，不是临场发挥：

- **Runbook**：每条 P1 告警对应一份，写清"看什么、常见原因、怎么处理、什么时候升级"
- **值班表**：明确谁在值班、怎么联系、升级路径是什么
- **权限预置**：值班人员必须提前有生产操作权限，不能故障时才申请
- **演练**：定期做故障演练（回滚演练、切流演练、混沌工程）
- **依赖清单**：每个服务的上下游依赖、联系人、SLA
- **故障看板**：一个页面能看到全系统健康状态，不用现场翻五个系统
