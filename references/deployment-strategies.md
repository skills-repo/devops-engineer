# 发布策略与回滚 Playbook

> 发布策略要解决的唯一问题：**把变更的爆炸半径和暴露时长压到最小**。
> 所有策略都是在「回滚速度」「资源成本」「实现复杂度」三者之间做交换。

## 一、策略选型

| 策略 | 回滚速度 | 资源成本 | 复杂度 | 适用 |
|------|---------|---------|--------|------|
| **重建（停机）** | 慢 | 1× | 极低 | 内部工具、可停机窗口 |
| **滚动更新** | 中（要滚回去） | 1× + 少量 | 低 | **大多数场景的默认选择** |
| **蓝绿** | **秒级切换** | **2×** | 中 | 关键服务、需要快速回滚 |
| **金丝雀** | 快（停止放量） | 1× + 少量 | 高 | 高风险变更、大流量服务 |
| **影子流量** | 无风险 | 2× | 高 | 重构验证，不返回结果给用户 |
| **Feature Flag** | **即时** | 1× | 中（需治理） | 功能级控制，与上述正交 |

**建议组合**：滚动更新（部署机制）+ Feature Flag（功能开关）覆盖 80% 需求，
高风险变更再叠加金丝雀。

## 二、滚动更新

```
副本逐批替换：v1 v1 v1 → v2 v1 v1 → v2 v2 v1 → v2 v2 v2
```

关键参数（K8s）：

```yaml
strategy:
  rollingUpdate:
    maxUnavailable: 0    # 保证容量不下降（需要集群有余量）
    maxSurge: 1          # 一次多起一个
minReadySeconds: 15      # 新 Pod ready 后再观察 15 秒才算成功
progressDeadlineSeconds: 600
```

**必要前提**：

1. **新旧版本能共存**。滚动期间两个版本同时在跑，API 和数据格式必须双向兼容
2. **优雅退出**。旧 Pod 收到 SIGTERM 后要先摘流量、等在途请求结束
3. **readiness 探针准确**。探针过早返回 ready 会把流量打给没准备好的实例

## 三、蓝绿部署

```
蓝（当前生产 v1）  ←── 100% 流量
绿（新版本 v2）    ←── 0%，先部署并验证

验证通过 → 流量整体切到绿 → 蓝保留一段时间作为回滚目标
```

**优点**：回滚就是把流量切回蓝，秒级。
**代价**：需要双倍资源；数据库是共享的，schema 变更仍需兼容两版。

适合：支付、交易等回滚速度优先于成本的服务。

## 四、金丝雀发布

```
1% 流量 → 观察 10 分钟 → 5% → 观察 → 25% → 50% → 100%
             ↓ 指标异常
          停止放量并回滚
```

### 关键：定义清楚"观察什么"

不是靠人盯屏幕，要有明确的自动判定指标：

```
错误率      canary 错误率 <= baseline × 1.1
P99 延迟    canary P99 <= baseline × 1.2
业务指标    转化率、下单成功率不低于 baseline × 0.95
```

任一不达标 → 自动停止放量并回滚。

工具：Argo Rollouts、Flagger 可以把上述规则声明化，自动做分析和回滚决策。

### 流量切分方式

| 方式 | 说明 |
|------|------|
| 按比例 | 最简单，随机分配 |
| 按用户 | 同一用户始终命中同一版本（避免体验跳变） |
| 按内部员工 | 先内测，风险最低 |
| 按地域 | 先小区域，出问题影响可控 |

**注意会话一致性**：按比例随机切分时，同一用户的连续请求可能落在不同版本，
如果两版行为不一致会造成诡异体验。有状态交互务必按用户切分。

## 五、Feature Flag：与部署解耦

```
部署 ≠ 发布
代码上线（关闭状态）→ 验证部署正常 → 打开 flag 给 1% 用户 → 逐步放开
```

这是最灵活的方式：出问题关 flag 即可，秒级生效，不需要重新部署。

### 治理规则（否则会变成技术债）

- 每个 flag 创建时**必须写下清理日期和责任人**
- 短期 flag（发布用）在全量后 2 周内删除
- 长期 flag（权限、订阅等级）单独归类，不与发布 flag 混在一起
- 定期审计：超过 90 天的发布类 flag 列出来强制清理
- flag 组合会指数级增加测试路径，**同时存活的发布类 flag 控制在 10 个以内**

## 六、数据库变更：最容易翻车的部分

应用可以秒回滚，**数据库不能**。所以所有 schema 变更必须**向后兼容**。

### 扩展-收缩模式（Expand-Contract）

以「重命名字段 `name` → `full_name`」为例：

```
阶段 1 扩展   加 full_name 字段（可空），不删 name
              部署应用：同时写两个字段，读 name
阶段 2 回填   后台任务把历史数据 name → full_name
阶段 3 切读   部署应用：读 full_name，仍双写
阶段 4 停写   部署应用：只读写 full_name
阶段 5 收缩   删除 name 字段
```

每个阶段之间都是可回滚的。跳步（直接改名）会导致：
新代码部署到一半时，旧实例还在读 `name`，而字段已经没了。

### 硬规则

| 操作 | 是否安全 |
|------|---------|
| 加可空字段 | ✅ |
| 加带默认值的字段（大表） | ⚠️ 可能锁表，看数据库版本 |
| 加索引 | ⚠️ 用 `CONCURRENTLY`（PG）/ `ALGORITHM=INPLACE`（MySQL） |
| 删字段 / 改字段名 / 改类型 | ❌ 必须走扩展-收缩 |
| 加非空约束 | ❌ 先回填再加，且分两次部署 |

**迁移脚本必须与应用版本解耦部署**——先跑迁移，确认无误，再部署应用。

## 七、回滚

### 回滚优先于修复

生产出问题时的默认动作是**回滚**，不是"我看看能不能快速修一下"。
修复在回滚之后从容进行。

```bash
kubectl rollout undo deploy/api           # K8s
# 蓝绿：切流量回蓝
# 金丝雀：停止放量，流量回 baseline
# flag：关闭开关
```

### 回滚前必须确认

- [ ] 数据库 schema 是否兼容旧版本？（不兼容则不能简单回滚）
- [ ] 有没有已经写入的新格式数据？旧版本能不能读？
- [ ] 是否有外部系统已经消费了新版本产生的消息？

**不可回滚的变更要事先识别出来**，这类变更需要更严格的灰度和更长的观察期。

### 回滚演练

回滚路径必须定期演练。很多团队的回滚流程只存在于文档里，
真出事时发现镜像已被清理、旧配置已覆盖、没人有权限执行。

## 八、发布检查清单

发布前：

- [ ] 变更是否向后兼容（API、数据格式、schema）
- [ ] 回滚方案是什么，多久能完成
- [ ] 监控和告警是否覆盖本次变更的影响面
- [ ] 是否需要灰度，灰度的判定指标是什么
- [ ] 依赖方是否需要提前通知
- [ ] 是否在低峰期（避免周五下午和长假前）

发布后：

- [ ] 观察四个黄金信号至少 15 分钟
- [ ] 检查错误日志有无新类型的错误
- [ ] 关键业务指标是否正常
- [ ] 确认后再进行下一批/下一个服务
