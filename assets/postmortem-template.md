### 关键时长

| 指标 | 数值 | 说明 |
|------|------|------|
| TTD（发现耗时） | __ 分钟 | 故障开始 → 有人知道 |
| TTA（响应耗时） | __ 分钟 | 有人知道 → 有人开始处理 |
| TTM（缓解耗时） | __ 分钟 | 开始处理 → 用户侧恢复 |
| 总影响时长 | __ 分钟 | |

> TTD 过长说明监控有盲区；TTA 过长说明告警路由或值班有问题；
> TTM 过长说明缺少快速回滚手段。三者要分开归因。

## 二、影响面

- **用户影响**：受影响用户数 / 占比、具体感知（报错？变慢？数据不一致？）
- **业务影响**：失败订单数、金额、SLA 违约情况
- **错误预算消耗**：本次消耗 __%，本周期剩余 __%
  （用 `python3 scripts/slo_budget.py --slo <目标> --total <总量> --bad <失败量>` 计算）
- **数据影响**：是否有数据丢失 / 脏数据？是否需要补偿修复？

## 四、根因分析

### 直接原因
<触发故障的那个变化是什么>

### 根本原因（5 Whys）

1. 为什么会出现故障？→
2. 为什么会这样？→
3. 为什么？→
4. 为什么？→
5. 为什么？→

> 停在"人为失误"就是没挖到底。继续问：为什么这个失误能通过所有防线？

### 为什么没有被更早拦住

逐层检查防线，标记哪一层失效以及原因：

- [ ] **代码评审**：为什么没看出来？
- [ ] **自动化测试**：为什么没覆盖这个场景？
- [ ] **CI 门禁**：为什么放行了？
- [ ] **预发环境**：为什么没复现？（环境差异在哪？）
- [ ] **灰度发布**：为什么没有先小流量验证？
- [ ] **监控告警**：为什么发现晚了？（有指标没告警？有告警没人看？）

## 六、行动项

> 每一项都要有**具体负责人**、**明确截止日期**、**可验证的完成标准**。
> 没有 owner 的行动项等于没有。优先做"降低同类事故影响"的，其次才是"防止完全相同的事故"。

| # | 类型 | 行动项 | 负责人 | 截止 | 状态 |
|---|------|--------|--------|------|------|
| 1 | 止血 | | | | 待开始 |
| 2 | 检测（缩短 TTD） | | | | 待开始 |
| 3 | 防御（阻止复发） | | | | 待开始 |
| 4 | 恢复（缩短 TTM） | | | | 待开始 |
| 5 | 流程/文档 | | | | 待开始 |

类型说明：
- **止血**：修复本次事故遗留的脏数据、临时补丁转正式方案
- **检测**：补监控、补告警、调整阈值，让下次更早发现
- **防御**：补测试、加门禁、改架构，让同类问题进不了生产
- **恢复**：备好回滚脚本、feature flag、降级开关，让下次恢复更快
- **流程**：更新 runbook、值班手册、发布规范
